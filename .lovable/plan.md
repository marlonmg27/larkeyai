# IDs numéricos (`id_int`) y nuevas llaves foráneas numéricas

Las llaves primarias UUID se conservan porque `users.id` está atado a `auth.users.id` y tu backend Python, Stripe y el frontend ya las usan. Encima de eso, cada tabla recibe un `id_int` numérico, único y autoincrementable, y se añaden columnas FK numéricas que apuntan a ese `id_int` para que de aquí en adelante las relaciones se hagan con números.

## 1. Columna `id_int` en cada tabla

`id_int bigint`, generado por identidad, `NOT NULL`, `UNIQUE`:

| Tabla | Numeración del backfill |
|---|---|
| `users` | 1..n por orden de `created_at` |
| `plans` | 1..n |
| `message_packs` | 1..n |
| `purchases` | 1..n por orden de `created_at` |
| `usage_balance` | 1..n |
| `whatsapp_connections` | 1..n |
| `stripe_events` | 1..n por orden de `processed_at` |

Cada inserción nueva obtiene el siguiente número automáticamente; los números no se reutilizan ni se reordenan.

## 2. Llaves foráneas numéricas nuevas

Cada relación existente gana su equivalente numérico, con FK real contra `id_int`:

| Tabla | Columna nueva | Referencia |
|---|---|---|
| `users` | `plan_id_int bigint` | `plans(id_int)` |
| `usage_balance` | `user_id_int bigint` | `users(id_int)` |
| `purchases` | `user_id_int bigint` | `users(id_int)` |
| `purchases` | `pack_id_int bigint` | `message_packs(id_int)` |
| `whatsapp_connections` | `user_id_int bigint` | `users(id_int)` |

- Se rellenan con el `id_int` correspondiente a partir del UUID que ya está en la fila.
- `ON DELETE CASCADE` donde hoy la FK UUID ya cascadea (`usage_balance`, `whatsapp_connections`, `purchases.user_id`), y `ON DELETE SET NULL` para `plan_id_int` y `pack_id_int`.
- Quedan nullable en esta migración: la app y tu backend Python siguen insertando por UUID hoy, y forzar `NOT NULL` rompería esos inserts. Cuando el código escriba siempre la columna numérica, se pasan a `NOT NULL` en una migración posterior.
- Índices en cada columna FK nueva.
- Las columnas UUID y sus FKs se mantienen en paralelo: son las que usan el trigger de `auth.users`, el webhook de Stripe y tu backend hoy.

## 3. Escritura automática de las FK numéricas

Para que las nuevas columnas se llenen solas desde el primer día sin tocar tu backend Python ni el webhook, un trigger `BEFORE INSERT OR UPDATE` por tabla deriva la columna numérica desde el UUID cuando venga vacía (por ejemplo `user_id_int := (SELECT id_int FROM users WHERE id = NEW.user_id)`). Así cualquier inserción por UUID —frontend, Stripe, FastAPI— queda consistente en ambos lados.

Se aplica a `users.plan_id_int`, `usage_balance.user_id_int`, `purchases.user_id_int`, `purchases.pack_id_int` y `whatsapp_connections.user_id_int`.

## 4. Permisos y tipos

- No se toca RLS ni los GRANT: las columnas nuevas heredan los permisos de su tabla.
- `handle_new_user` se actualiza sin cambiar su comportamiento visible (sigue insertando por UUID; el trigger nuevo completa el número).
- Se regeneran los tipos del cliente para que `id_int` y las columnas FK numéricas existan en TypeScript.

## Detalles técnicos

- `GENERATED BY DEFAULT AS IDENTITY` (no `ALWAYS`), con `START WITH max+1` tras el backfill, para que el backend pueda insertar sin mencionar `id_int` y también forzar un valor si hace falta.
- El orden por migración y por tabla es: `ADD COLUMN` nullable → backfill → `SET NOT NULL` (solo `id_int`) → `ADD GENERATED ... IDENTITY` → `UNIQUE` → columnas FK numéricas + backfill + FK + índice → triggers.
- Ninguna función SQL existente (`activate_client`, `apply_subscription_event`, `add_purchased_messages`, `decrement_messages`, `reset_expired_usage_balances`) cambia de firma: siguen recibiendo UUID, así que tu backend y el webhook no se rompen.
- `stripe_events` solo recibe `id_int` (no tiene relaciones).

## Fuera de alcance

- No se elimina ni se cambia el tipo de ninguna PK o FK UUID existente (eso rompería el login y tu backend en producción).
- No se cambian las firmas de las funciones RPC a numérico; si lo quieres, lo hago después como funciones nuevas en paralelo.
- Sin cambios de UI.
