# IDs numéricos, únicos y autoincrementables (aditivos)

Las llaves primarias UUID se conservan: `users.id` está atado a `auth.users.id` y todas las FKs (`purchases.user_id`, `purchases.pack_id`, `usage_balance.user_id`, `whatsapp_connections.user_id`, `users.plan_id`) más tu backend Python y Stripe ya las usan. En vez de cambiar el tipo, cada tabla recibe una columna numérica adicional, secuencial y única, apta para mostrar y referenciar de forma legible.

## Qué se agrega

Columna `numero bigint`, generada por identidad, `NOT NULL` y `UNIQUE`, en cada tabla de `public`:

| Tabla | Numeración |
|---|---|
| `users` | 1..n por orden de `created_at` |
| `plans` | 1..n |
| `message_packs` | 1..n |
| `purchases` | 1..n por orden de `created_at` |
| `usage_balance` | 1..n |
| `whatsapp_connections` | 1..n |
| `stripe_events` | 1..n por orden de `processed_at` |

Comportamiento: cada inserción nueva obtiene el siguiente número automáticamente; nunca se reutiliza ni se reordena, y las filas existentes conservan el número asignado en la migración.

## Cómo se aplica

Una sola migración aditiva, por tabla:

1. `ALTER TABLE ... ADD COLUMN numero bigint` (nullable de entrada).
2. Backfill con `row_number()` sobre el orden cronológico indicado arriba.
3. `ALTER COLUMN numero SET NOT NULL`.
4. `ALTER COLUMN numero ADD GENERATED BY DEFAULT AS IDENTITY (START WITH <max+1>)` para que la secuencia siga donde termina el backfill.
5. `ADD CONSTRAINT ..._numero_key UNIQUE (numero)`.

No se toca RLS ni los GRANT existentes: la nueva columna hereda los permisos de la tabla, así que el frontend y el backend la leen igual que el resto.

Después de la migración se regeneran los tipos del cliente para que `numero` exista en TypeScript.

## Detalles técnicos

- `GENERATED BY DEFAULT` (no `ALWAYS`) permite que tu backend Python inserte filas sin mencionar `numero`, y también forzar un valor si algún día hace falta.
- `stripe_events` no tiene políticas RLS (solo service role); la columna queda disponible para el backend igualmente.
- Ninguna función SQL existente (`activate_client`, `apply_subscription_event`, `add_purchased_messages`, etc.) necesita cambios: siguen operando por UUID.

## Fuera de alcance

- No se cambia ninguna PK ni FK a numérico.
- No se muestra `numero` en la UI todavía; si quieres exponerlo (p. ej. "Cliente #12" o folio de compra en el dashboard), lo agrego en un paso aparte.
